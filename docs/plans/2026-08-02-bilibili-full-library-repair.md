# B站全库记录修复计划（2026-08-02）

## 状态与目标

本计划已进入分批执行阶段。目标是逐一尝试修复默认库中现有的全部 B站 article 记录：使用 article
详情重新取得完整正文和正文图片，按原平台 ID 幂等更新，且全过程可恢复、可审计、可回滚。

截至 2026-08-03，临时库 sidecar 中有 20 条 `succeeded`，均已通过逐条正文、图片、来源字段和
数据库不变量验收，并以单事务原位回写默认库；5 条为 `retryable`，其余 2,984 条仍为 `pending`。
默认库当前仍为 3,009 个唯一 B站平台 ID，其中 20 条具有 `detail_observed` 和历史修复证据；这只表示
首批结果已落库，不表示 100 条演练或全库修复已经完成。

计划基线为 3,009 条 B站记录。开始执行前必须重新生成源清单并核对实际数量，不能把 3,009 当作
永不变化的常量。全部源记录都进入处理清单；明确删除、私密或平台永久不可用的记录也必须留下
决定性证据和最终状态，不能静默跳过。

本计划不是普通关键词抓取，不使用 `target-new-posts` 或 `source-exhausted` 判断完成，也不改变
`crawl_jobs`、搜索 checkpoint、候选记忆、累计摘要或任一平台默认启用状态。

- `-509`、传输/解析失败采用有限退避；失败候选不进入已处理集合，恢复页不前移。
- 自动测试覆盖详情正文、多图、短文、限流、解析失败、安全前沿、幂等 upsert、全局指数冷却、

  `279/3`、`283/3` 恢复为详情 `2947/6`、`1658/7`；一条真实短文为 `266/1` 对详情
  `264/1`，证明验收依赖详情证据，不依赖长度必然增加。

## 不变量

回填实现和执行必须同时守住以下边界：

1. 只处理执行开始时源清单中的 `platform_key='bilibili'` 行；不从搜索接口发现或插入新 ID。
2. 每个成功项只能更新原 `web_posts.id`；主表 B站行数、平台 ID 唯一集合和非 B站行完全不变。
3. 成功前不修改目标行。请求失败、限流、解析失败或字段门禁失败时保留原行并写侧车状态。
4. 成功更新同时重建该帖的 `web_post_images`，图片数必须等于本次详情解析后的去重正文图片数。
5. 保留原关键词、原平台 ID、canonical URL 和原 artifact 关联；`raw_sample_json` 同时保留搜索摘要、
   搜索预览与本次详情来源，不能覆盖后丢失旧证据。
6. 不把搜索预览图算作正文图。当前 Opus 使用段落 `pic.pics`，旧 article 使用正文 HTML；只有没有
   这些结构时才回退到详情响应的旧式图片数组。
7. 正文短于旧值不自动失败，正文长于旧值也不自动成功；必须通过详情状态、受信任来源、正文解析、
   图片和现有必需字段门禁。
8. 回填不计入任何新抓取数量，不创建来源耗尽证据，不推进任何发现前沿。

## 计划中的独立入口与状态

先实现独立入口 `scripts/repair_bilibili_articles.py`，不得让普通关键词搜索承担历史修复。入口默认
必须是 dry-run，并要求显式的输入库、输出状态库和批次上限；写默认库还必须额外提供明确的
`--apply` 开关以及与备份清单匹配的基线哈希。

可恢复状态保存到独立 sidecar SQLite，不写通用抓取 checkpoint。至少记录：

- repair run ID、源数据库绝对路径与 SHA-256、源清单 SHA-256、代码 commit；
- `web_posts.id`、平台 ID、原正文 SHA-256、原正文长度、原图片数；
- 状态 `pending`、`succeeded`、`retryable`、`permanent_unavailable`、`invalid_detail`；
- 请求次数、最后业务/HTTP 错误、下一次允许时间、详情来源、详情正文长度和图片数；
- 成功更新时的更新时间、更新后正文 SHA-256 和图片 URL 集合 SHA-256。

恢复时只选择 `pending` / 到期的 `retryable` 项；`succeeded` 项必须核对目标库当前哈希仍与状态库
一致后跳过。若目标行在清单生成后被其他进程修改，使用乐观锁停止该项并报告冲突，不盲目覆盖。

## 执行阶段

### 1. 实现与隔离测试

- 复用已经验收的 article 详情请求、正文清洗、图片提取和正式门禁函数，不复制一套语义不同的解析器。
- 为 sidecar 状态迁移、恢复、乐观锁、永久不可用分类和 dry-run 报告增加自动测试。
- 在临时 SQLite 中复制固定样本，至少覆盖当前 Opus 多图、旧 article HTML 图、真实短文、无图、
  `-509`、无效 JSON、删除/私密和更新冲突。
- 同一批样本连续执行两次，第二次更新数必须为 0，主表和图片表不得产生重复行。

### 2. 冻结源清单与备份

停止对默认库的其他写入后，用 SQLite 在线备份 API 或 `.backup` 创建一致性备份，不用普通文件复制
替代事务一致性。记录原库、备份和源清单的 SHA-256、字节数、时间与 Git commit。

源清单至少包含 `web_posts.id`、`platform_post_id`、keyword、canonical URL、artifact_dir、正文哈希/
长度和正文图片数，并满足：

- B站平台 ID 非空且无重复；
- 清单行数等于当时默认库 B站行数；
- `PRAGMA quick_check` 返回 `ok`，`PRAGMA foreign_key_check` 无结果；
- 备份库与源库的 B站 ID 集合及内容哈希一致。

任何一项不满足都停止，不能进入真实请求或写入。

### 3. 临时库演练

从一致性备份派生临时工作库，按固定 20 条样本先演练，再扩大到 100 条。真实请求必须保持单线程，
批次大小和会话请求数不得超过当时 crawl policy 的有效预算；所有随机等待和重试写入 sidecar。

每批验收：

- `succeeded + retryable + permanent_unavailable + invalid_detail` 等于本批计划数；
- 成功项主表 ID 不变、关键词不变、`content_detail_status=detail_observed`、来源受信任；
- `web_posts.post_images_count` 等于 `web_post_images` 中 content 角色行数，也等于详情解析去重图片数；
- 失败项原正文哈希和图片关系完全不变；
- 重跑批次无重复、无额外插入。

如果 100 条演练出现未解释的正文/图片差异、重复、状态丢失或数据库校验失败，回到实现阶段，不进入
默认库。

### 4. 默认库分批回填

只有临时库演练报告通过后，才能以冻结清单和备份哈希启动 `--apply`。每个小批次使用短事务：先在
事务外取得并验证详情，再在事务内核对原行乐观锁，更新一条主表及其图片关系，然后提交 sidecar
成功状态。默认串行；不得为了速度提高并发。

遇到 `-509`、HTTP 429/5xx、超时或解析失败时按详情客户端有限退避；仍失败则标记 `retryable`，
停止当前请求会话并在冷却后恢复。明确的删除、私密或不存在只有在平台返回已知且经过测试的决定性
业务码时才记为 `permanent_unavailable`；未知非零码一律不冒充永久结论。

每批结束保存报告并执行数据库快速检查。发生以下任一情况立即停止后续批次：B站行数或 ID 集合
变化、非 B站行被修改、重复平台 ID、外键错误、成功项图片计数不一致、失败项被覆盖、sidecar 与
目标库哈希不一致。

### 5. 收尾复验

对源清单全部 3,009 条（或执行时实际数量）逐一取得最终状态。完成报告必须分别给出：

- 源清单数、已尝试数、详情成功并更新数；
- 永久不可用数及业务码分布；
- 仍待重试数、无效详情数、写冲突数；
- 更新前后正文长度分布和图片数量分布，但不把“长度增加”当完成门槛；
- B站/全库行数、唯一平台 ID、图片关系、`quick_check`、`foreign_key_check`；
- 备份、清单、sidecar、最终数据库和报告的路径与 SHA-256。

从成功项分层随机抽样，至少覆盖当前 Opus、旧 article、长文、多图、短文和图片数未变化记录，重新
读取真实详情并核对正文哈希/图片 URL 集合。所有待重试清零，或被逐条转为有决定性证据的永久不可用/
无效详情后，才能宣布“已尝试修复全库”；只有每条可用 article 均成功更新后，才能宣布“可用记录
全部修复完成”。

## 回滚

默认库执行期间禁止删除一致性备份。若批次级不变量失败，先停止写入并保存当前库、sidecar 和日志，
不要在问题未定位时继续或手工修补。需要整体回滚时，先验证备份 SHA-256 和 SQLite 完整性，再在
停止所有写入进程后以备份替换；回滚动作、操作者、时间和替换前后哈希必须写入事件报告。
